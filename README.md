# AI-агент проверки целевого использования льготных кредитов — тестовое задание

Модуль интеллектуальной обработки документов для проверки комплектности пакета
документов по льготному сельхоз-кредиту: классификация типа документа,
извлечение ключевых полей и проверка соответствия предмета оплаты программе.


## 1. Как запустить проект

```bash
pip install -r requirements.txt
cp .env.example .env        # вставьте GOOGLE_API_KEY, если хотите включить LLM-путь
pytest -m unit              # быстрые тесты, без сети и без ключа
```

Без `GOOGLE_API_KEY` (или без пакетов `langchain*`) весь пайплайн продолжает
работать — каждая функция автоматически откатывается на regex/keyword-fallback
(это требование задания: код должен запускаться локально без ключей).

Запуск пайплайна на всём датасете `data/` с сохранением JSON-отчётов в `output/`:

```bash
python -m src.graph
```

Печать таблиц из RESULTS.md + confidence-график (сохраняется в `output/`):

```bash
python -m scripts.demo
```

Полный прогон тестов, включая integration-тесты (требуют `GOOGLE_API_KEY`):

```bash
pytest                       # unit + integration (integration skip-нутся без ключа)
```

## 2. Технологии и почему

| Технология | Зачем |
|---|---|
| **Python 3.12** (совместимо с 3.11+) | язык задания |
| **LangChain + langchain-google-genai** | единый интерфейс к Gemini (`gemini-3.5-flash`) |
| **Pydantic + JsonOutputParser + PromptTemplate** | структурированный JSON-вывод от LLM (схема → инструкции → парсинг), см. раздел 7 |
| **LangGraph** (`StateGraph`, `add_conditional_edges`) | явный, тестируемый граф с настоящим ветвлением вместо неявной цепочки if/else |
| **pytest** (`-m unit` / `-m integration`) | unit-тесты работают офлайн; integration-тесты бьют по реальному API и скипаются без ключа |
| **regex / stdlib** | весь fallback-путь — без единой внешней зависимости, чтобы пайплайн гарантированно запускался локально |
| **matplotlib** (опционально) | график уверенности классификации в `scripts/demo.py` |

Gemini выбран согласно заданию (бесплатный тариф Google AI Studio,
`gemini-3.5-flash`, ~1500 запросов/день, 15/мин — see `.env.example`).

## 3. Архитектура

```
src/
  utils.py            # OCR-нормализация цифр, парсинг русских дат, чисел прописью
  extractor.py         # extract(text) -> dict
  classifier.py         # classify(text) -> (type, confidence)
  subject_checker.py    # check_subject(subject) -> (bool, confidence, reason)
  graph.py              # 2 LangGraph-пайплайна + CLI (`python -m src.graph`)
data/                  # тестовый датасет (7 документов + subjects_test.txt)
output/                # JSON-отчёты, reconciliation.json, график
tests/                 # pytest, маркеры unit/integration (49 тестов)
scripts/demo.py        # печать таблиц + confidence-график для RESULTS.md
```

**graph.py содержит два графа** (подробности изменений — раздел 7):

1. **Граф обработки документа** (`build_graph`, `DocState`): `classify` →
   `extract` → *условное ребро* → `check_subject` **или**
   `skip_subject_check` → `finalize`. `finalize` формирует
   `status: "ok" | "requires_manual_review"` и список `notes` с
   человекочитаемыми причинами (низкая уверенность классификации,
   отсутствующие обязательные поля, несоответствие предмета оплаты
   программе) — как описано в бизнес-кейсе (TO BE, п. 6-7 `test_credit.pdf`).
2. **Граф пост-контроля** (`build_reconciliation_graph`, `ReconcileState`):
   группирует уже обработанные документы по ИНН контрагента и (через
   условное ребро) либо сверяет суммы между документами одной сделки, либо
   помечает, что сверять не с чем (один документ). Реализует пункт TO BE
   бизнес-кейса «сопоставляет данные из авансового платежа с данными
   закрывающих документов по сумме» — результат в `output/reconciliation.json`.

**Каждая из трёх функций (`extract`, `classify`, `check_subject`)** сначала
пробует LLM-путь (`_*_via_llm`, только если задан `GOOGLE_API_KEY` и
установлен `langchain-google-genai`), и при отсутствии ключа, отсутствии
пакета, сетевой ошибке или невалидном JSON-ответе — **прозрачно** откатывается
на rule-based fallback. Ошибка в LLM-вызове никогда не приводит к падению
пайплайна.

**Ключевая идея классификатора:** документы в датасете постоянно
*ссылаются* друг на друга по имени («Основание: Договор поставки № ...»,
«Спецификация № 1»), поэтому наивный поиск слова «договор» не работает —
он сработает почти на каждом документе. Решение: заголовок документа в
этих образцах всегда набран **заглавными буквами** и стоит **в начале**
файла, а ссылка на другой документ — обычным регистром в теле текста.
Паттерны-заголовки проверяются с учётом регистра и позиции (первые ~100
символов), контекстные фразы (банковские реквизиты для счёта, «именуемое в
дальнейшем» для договора, «Работы выполнены» для акта) — по всему тексту,
т.к. они не встречаются как случайные цитаты.

## 4. Компромиссы

- **Извлечение полей — regex, не NER/ML.** На 7 документах ML-модель не
  обучить; регулярки, привязанные к формату документа (таблица `|...|`,
  метки «Поставщик:», «Предмет:»), дают 100% полей на 6 чистых документах,
  но переносятся на новый формат документа не автоматически.
- **`contractor`/`subject` определены как «сторона, поставляющая
  товар/услугу»** (Поставщик/Продавец/Исполнитель), а не как participant
  вообще — это осознанный выбор, продиктованный тем, что во всех образцах
  именно эта сторона является объектом проверки целевого назначения.
- **OCR-нормализация — точечная, не полная.** Заменяются только
  визуально-похожие символы в уже понятных числовых контекстах (дата,
  сумма, ИНН) — этого хватило, чтобы восстановить 3 из 5 полей на
  `scan_ocr_001.txt`, но `contractor`/`subject` там искажены на уровне
  целых слов (кириллица/латиница вперемешку), и без полноценного
  OCR-post-processing восстановить их нельзя — сознательно оставлено
  `None`, а не угадано.
- **Порог классификации (`CONFIDENCE_GAP_THRESHOLD = 15`)** подобран
  эмпирически на 7 документах — см. RESULTS.md.
- **check_subject — категориальный keyword-matching**, а не эмбеддинги/
  fuzzy-similarity: на 17 тестовых примерах даёт 14/14 верных PASS/FAIL и
  прозрачное объяснение (какая категория совпала); для EDGE-кейсов не
  претендует на «единственно верный» ответ — так и задумано заданием.
- **LLM-путь не протестирован end-to-end** в среде разработки (нет доступа
  в интернет в песочнице) — код написан по стандартным паттернам
  LangChain/`ChatGoogleGenerativeAI`, но реальный вызов Gemini стоит
  проверить с реальным ключом перед сдачей (`pytest -m integration`).

## 5. Как проверить работу

```bash
pytest -m unit -v                 # 49 unit-тестов, включая обязательные
                                   # assert-ы из задания
python -m src.graph               # прогон data/ -> output/*.json + reconciliation.json
python -m scripts.demo            # таблицы + confidence-график
```

Ожидаемый результат `pytest -m unit`: все тесты зелёные, без сети и без
`GOOGLE_API_KEY`. Ожидаемый результат `python -m src.graph`: 6 из 7
документов получают `status: "ok"`, `scan_ocr_001.txt` —
`"requires_manual_review"` (низкая уверенность классификации + не
извлечён `subject`) — то есть именно то поведение, которое описано в
бизнес-кейсе как желаемое (TO BE, критерий "низкая уверенность → ручная
проверка"). Плюс блок пост-контроля: 5 документов с ИНН `7701234567`
(договор/спецификация/счёт/акт/OCR-скан одной сделки) сверяются по сумме
и получают `"amount_consistent": true`.

## 6. Примеры вызовов

```python
from src.extractor import extract
from src.classifier import classify
from src.subject_checker import check_subject

extract("Сумма: 1 250 000,00 руб.")
# {'amount': 1250000.0, 'date': None, 'inn': None, 'contractor': None, 'subject': None}

classify("Счёт на оплату №12 от 01.03.2025 ...")
# ('invoice', 0.81)

check_subject("Поставка минеральных удобрений (карбамид марки Б)")
# (True, 0.9, 'предмет относится к категории «агрохимия (удобрения, СЗР)»')
```

CLI:

```bash
python -m src.graph                    # обработать data/ -> output/*.json
python -m scripts.demo                 # таблицы + график
```

График уверенности классификации (`scripts/demo.py`):
`output/classification_confidence.png`.

Все 49 тестов (`pytest -m unit`) проходят на regex/keyword-fallback пути
без сети — это единственный путь, который можно было проверить в среде
разработки; LLM-путь по-прежнему стоит прогнать через
`pytest -m integration` с реальным `GOOGLE_API_KEY` перед сдачей.

См. также `RESULTS.md` (итоговые таблицы и разбор слабых мест)
